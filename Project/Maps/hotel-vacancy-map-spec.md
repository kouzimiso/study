# ホテル空室・観光地分布マップツール 仕様書

最終更新：実装フェーズ反映版（バックエンド／フロントエンド一次実装済み）

## 1. 目的
盆休みなどの繁忙期に、関東近郊・北海道など広範囲を対象に、ホテルの空室状況を地図上で可視化し、観光地の分布と重ね合わせることで「空いている宿泊エリア」を見つけやすくする。

## 2. 想定ユーザー・公開方針
- 作成者本人が旅行先を検討する際に使う個人ツールとしてスタートし、**将来的には一般公開も視野に入れる**
- **ログイン・アカウント登録は不要**。誰でも閲覧できる、Googleマップ的な「付加情報レイヤー」という位置付け
- 公開を見据え、楽天トラベルAPIの利用規約対応（表示要件・アフィリエイト表記等）、アクセス増加時のレート制限対策、無料枠を超えた際のコスト設計を織り込み済み

## 3. 対象範囲
- 地域：**まずは関東近郊・北海道からスタートし、将来的には日本全国への展開を見据える**
- 期間：日付を1日単位で指定して検索（範囲日程はこの1日データの集合として扱う）
- 宿泊施設：楽天トラベル掲載施設

## 4. 主な機能

### 4.1 空室検索機能
- 検索・保存の単位は「1日」。日ごとに独立して管理するため、「最初の3日は穴場、後半は混雑」のような日別の傾向判定が可能
- 同一日付の検索結果が既に**本日**取得済みの場合は再取得せず、フロント側で「更新しますか？」の確認バナーを出す。確認は**日付が変わったタイミング（1日1回）のみ**。この制約はクライアントの申告に頼らず、サーバー側（`fetched_at`の日付比較）でも強制する

### 4.2 地図表示機能（ヒートマップ）
- 固定グリッドではなく、**ホテルの分布密度に応じた可変の「担当範囲」**を単位とする
  - ホテル密集地（都市部）→ 担当範囲は狭い
  - ホテル疎な地域（郊外・地方）→ 楽天APIの検索半径上限（3.0km）まで広く取る
  - 半径 = min(3.0km, 最近傍ホテルまでの距離 ÷ 2)
- 担当範囲の計算は重い処理のため、**初回（および地域拡大時）のみローカルで実施**し、以降は使い回す
  - 週1回程度、「周辺のホテル構成が変わっていないか」を軽量チェックし、変化があったホテルだけ再計算対象（`dirty`フラグ）としてマークする
- 日付を切り替えると、その日の担当範囲別の空室件数がヒートマップ（赤＝空き少・混雑 → 緑＝空き多・穴場）で表示される

### 4.3 観光地表示機能
- OpenStreetMap Overpass APIから、現在の地図表示範囲内の観光地POIを取得し、地図に重ねる（ズームレベル9未満では取得しない）

### 4.4 定期更新機能
- Cloudflare WorkerのCronで定期実行
  - 平日：日々の空室巡回（担当範囲ごとに楽天空室検索APIを呼び出し、結果をキャッシュ）
  - 日曜：ホテルの周辺構成に変化がないかの軽量チェック
- Workers無料枠のsubrequest上限に配慮し、**1回のCron実行では一部ホテルだけ処理し、続きは次回起動に持ち越す**バッチ方式

## 5. システム構成（実装済み）
```
[① scripts/sync-hotels.mjs]（ローカル実行・初回/地域拡大時のみ）
   楽天施設検索APIで対象地域の全ホテル座標を収集 → hotels.sql / hotels.json

[② scripts/compute-territories.mjs]（①の後、ローカル実行）
   hotels.json からホテルごとの担当範囲(半径)を計算 → territories.sql

[③ D1データベース]（Cloudflare、無料枠）
   hotels / hotel_territory / vacancy_snapshots / job_state

[④ Cloudflare Worker]（無料枠）
   ・HTTPエンドポイント（/api/heatmap, /api/status, /api/refresh, /api/admin/dirty-hotels）
   ・Cronで日々の空室巡回＋週次の周辺構成チェック

[⑤ フロントエンド]（Cloudflare Pages、無料枠）
   frontend/index.html（単一HTML、Leaflet.js + CARTOダークタイル）
   + Overpass APIから観光地POIをブラウザから直接取得して重畳表示
```
- ホスティング：Cloudflare Workers / D1 / Pages（すべて無料枠）
- 代替案：Vercel Functions + Supabase（無料枠）

## 6. データソース
| データ | 取得元 | 備考 |
|---|---|---|
| ホテル一覧・座標 | 楽天トラベル施設検索API（SimpleHotelSearch） | 要アプリ登録（無料）。`applicationId`+`accessKey`必須 |
| ホテル空室情報 | 楽天トラベル空室検索API（VacantHotelSearch） | 同上。`datumType=1`で世界測地系(度)指定、`searchRadius`は0.1〜3.0km |
| 観光地POI | OpenStreetMap Overpass API | 登録不要・無料 |
| 地図タイル | CARTO Dark Matter（OpenStreetMapベース） | 無料、要帰属表示 |

- **施設詳細・予約への導線は楽天アフィリエイトURLを経由**して楽天トラベルへ遷移させる（APIレスポンスのアフィリエイトURLをそのままリンク先に使用し、利用規約対応をしやすくする）

## 7. データベース設計（D1）
| テーブル | 役割 |
|---|---|
| `hotels` | ホテル一覧（施設番号・名称・座標・地域） |
| `hotel_territory` | ホテルごとの担当範囲(半径)・最近傍距離・近隣ホテル集合・`dirty`フラグ |
| `vacancy_snapshots` | 日付×ホテル単位の空室件数スナップショット（`fetched_at`で鮮度管理） |
| `job_state` | Cronバッチ処理の進捗（ジョブ種別ごとにカーソル位置を保持） |

## 8. API仕様（Cloudflare Worker）
| エンドポイント | 説明 |
|---|---|
| `GET /api/heatmap?date=YYYY-MM-DD` | 指定日のヒートマップ用GeoJSON（ホテルごとの担当範囲＋空室件数） |
| `GET /api/status?date=YYYY-MM-DD` | その日のデータ有無・最終取得日時・更新確認要否 |
| `POST /api/refresh?date=YYYY-MM-DD` | 手動更新をトリガー（同日中に取得済みなら何もしない） |
| `GET /api/admin/dirty-hotels` | 周辺構成が変化し、担当範囲の再計算が必要なホテル一覧 |

## 9. フロントエンド仕様
- 単一HTMLファイル（`frontend/index.html`）。Leaflet.js（CDN: cdnjs.cloudflare.com）+ CARTOダークタイル
- 主要UI：
  - 宿泊日ステッパー（前日／翌日／日付直接指定）
  - 観光地表示トグル
  - 更新確認バナー（「更新しますか？」→ Yes/No）
  - 凡例（空き少＝赤 〜 空き多＝緑のグラデーション、観光地＝金ドット）
- `CONFIG.API_BASE`が未設定の場合は**デモモード**でダミーデータを表示し、Worker未デプロイでも動作確認できる
- 外部リソースは許可済みCDN（cdnjs.cloudflare.com）を使用。読み込み失敗時は画面上にエラーメッセージを表示するフォールバックを実装済み

## 10. 非機能要件
- コストは無料枠内に収める。アクセスや処理量が増えても、**課金ではなくアクセス制限・キャッシュ延長で対応**する方針を優先（全国展開時は需要の高いエリア・時期を優先して更新するなどの制御が必要）
- 楽天APIのレート制限を考慮し、巡回間隔・バッチサイズを調整可能な設定値として持つ
- **個人情報を扱わない設計を原則とする**（Googleマップ的な付加情報レイヤーの位置付け）
  - アカウント登録・ログイン機能は持たない
  - アクセス解析はCookieレス・集計のみのツール（Cloudflare Web Analytics）に限定し、個人特定につながるログ保存は行わない

## 11. 拡張候補（将来検討・現時点のスコープ外）
- **お気に入り保存機能**：施設やエリアをブックマークできる機能
- **空き通知機能**：指定条件で空きが出た際にメール／LINE等で通知する機能
  - ※上記2つはメールアドレス等の個人情報を扱うことになるため、実装時にプライバシーポリシー・保管方針を別途設計する
- **コントリビューター方式による地域拡張**：自分の楽天APIキーを登録した人が新しい地域の巡回に参加できるようにする
  - 参加者ごとのAPIキー・レート制限で並行動作させ、無料枠のスケール制約を分散して緩和
  - 「ログイン」はメール等を集めるアカウント制ではなく、楽天APIキーの入力自体を本人確認代わりにする方向で検討（個人情報を扱わない方針との整合）
  - 検討事項：地域担当の重複時の扱い、誤ったパラメータでの更新の防止、楽天API利用規約との整合確認
- 施設の絞り込み条件（価格帯・部屋タイプなど）の追加
